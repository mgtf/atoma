# Trajectory predictability as a trust regulariser — design proposal, 2026-09-09

Status: **proposal for review, not a contract.** Nothing below is normative
until the owner answers section 11 and the accepted parts land as ONE reviewed
commit, per the COOLING-OFF rule in the root `AGENTS.md`. Every number in this
document is regenerated by the command in section 4; a reader who finds the
numbers and the command disagreeing should trust the command.

## 1. The ask, in the owner's terms

> "Comment pourrais-je implémenter ça dans Atoma ?"

"Ça" is the result of a grokking experiment: a one-layer transformer trained on
`(a + b) mod 113` generalises 3x sooner when a small probe is trained to predict
the MLP's hidden state from its input and the probe's error is added to the loss
as a regulariser. A stencil ablation over temporal offsets shows that asking for
**stability across time** (`k=-1`, `k=+1`) helps at least as much as asking for
**coherence at the same instant** (`k=0`).

## 2. What transposes and what does not

Atoma trains no weights. There is no gradient to add a term to, so the
literal mechanism is out. What transposes is the principle underneath it:

> A system whose internal trajectory is predictable from its input generalises;
> the error of a cheap predictor of that trajectory is a usable signal.

| Paper | Atoma |
|---|---|
| MLP input | the subtask text and capability an atom receives |
| hidden state | the observed trajectory: ordered tool names, executing tier, cost band |
| the probe | a zero-token predictor of the trajectory, built from the trace store |
| probe error | the distance between predicted and observed trajectory |
| regularisation | what the error modulates: trust fast path, skill credit, promotion |
| weight decay | the existing trust counters and the `trustThreshold()` rule |
| probe discarded after training | the predictor never runs inside a run and never calls a model |
| leak-free buffer | the predictor reads traces only, never verdicts or expected results |

Two things do not transpose and must be said plainly:

- The paper's regulariser acts continuously, on every step. Atoma's only
  "learning" is discrete: a trust counter, a skill credit, a compile. The
  signal can therefore weigh on **decisions that already exist**, never steer
  a run in flight. That is also what keeps it inside the sentinel's contract
  ("an observer; its only power is a journal row").
- The paper measures generalisation on held-out inputs. Atoma has no held-out
  set. The nearest observable is **the same capability, on a later goal,
  taking a trajectory of the same shape**. Section 4 shows this is measurable
  today.

## 3. What exists today, verified

Read before designing anything; two of these change the shape of the proposal.

- **Three partial probes already exist and none is scored against what
  actually happened.** `prefilterStrategy` (`src/atoms/cost.ts`) predicts a
  strategy before planning; its verdict is never compared to the plan the
  supervisor then produced. A compiled skill's probe manifest is a full
  prediction of the execution path; only the result is checked, not the path.
  The `skill.match` event names the recipe expected to drive the child; nothing
  measures how far the child strayed from it, except the validator's
  narrative adherence check.
- **The "mismatch withholds reward" gesture is already built, for one kind of
  mismatch.** `PositiveVerdict.proofUncovered` (`src/atoms/proofCoverage.ts`,
  applied in `L2Atom.ts` around the credit gate) withholds atom trust, skill
  credit, distillation and promotion on an approved result whose declared
  proof obligation has no transport-observed attestation. The `skill` event
  `op: 'credit-withheld'` is the journal spelling. The proposal below adds a
  second reason to reach the same gate; it does not add a second gate.
- **The trace already carries the trajectory.** `VizToolEvent` has `name`,
  `actor {tier, name}`, `llmEventId`, `durationMs`, `error`, `branchId`.
  `VizTrustEvent` carries the counters after each move. `VizSkillEvent`
  carries `match/inject/success/credit-withheld` with `skillId` and
  `l1AtomId`. No new field is needed to compute the score below; only the
  goal's identity is missing from the tool event and is recoverable through
  `llmEventId`.
- **The sentinel is the right home for the first stage and it already
  forbids the wrong one.** `src/sentinel/rules.ts` rules are pure functions
  over a bounded event window, emit at most a journal row, and the file's
  header says adding a rule is adding a mechanism under COOLING-OFF. The
  `slow-tool-outlier` rule already needs three samples before speaking;
  the proposal borrows that discipline.
- **Trust counters are saturated on the local store.** Every `trust` event in
  the ten traces under `runs/` reads `n/0`. Trust cannot currently tell a
  clean run from a chaotic one, because both increment the same counter.
  This is the gap the proposal targets, and it is the reason `k=0` alone is
  not enough (see the ablation reading in section 5).

## 4. The measurement that justifies going further

Ten real traces are in `runs/` on this machine (2026-08-22 and 2026-09-07,
`build-app` profile). The command below groups every tool event by actor and
prints the ordered tool-name trajectory, the trust moves and the skill events.
It is the witness for every claim in this section; rerun it before quoting.

```bash
node -e '
const fs=require("fs");
for (const f of fs.readdirSync("runs").filter(x=>x.endsWith(".json")&&x!=="index.json")) {
  const t=JSON.parse(fs.readFileSync("runs/"+f)); const ev=t.events||[];
  const st=t.result? (t.result.summary??"").slice(0,50) : (t.error?"ERROR":"no-result");
  console.log(f.slice(0,19),"|",st,"| task="+String(t.task?.description??"").slice(0,60));
  const byActor={};
  for (const e of ev){ if(e.kind!=="tool")continue; const a=e.actor?e.actor.name+"@L"+e.actor.tier:"?"; (byActor[a]??=[]).push(e.name);}
  for (const [a,seq] of Object.entries(byActor)) console.log("   ",a,seq.length,seq.join(">").slice(0,180));
  const trust=ev.filter(e=>e.kind==="trust").map(e=>`${e.child?.name}:${e.subject}:${e.successes}/${e.failures}`);
  console.log("    trust:",trust.join(" "));
  const sk=ev.filter(e=>e.kind==="skill").map(e=>e.op+":"+e.skillId); console.log("    skills:",sk.join(" ").slice(0,200));
}'
```

What it shows, read on 2026-09-09:

| goal (same text, same skill matched) | run | L1 actor | tool events | outcome | trust move |
|---|---|---|---|---|---|
| Node HTTP server, `node-http-static-json-api` | 10:33 | Methane | 18 | delivered, 3 phases | 7/0 → 8/0 |
| same | 10:47 | Methane + Dopamine + Adrenaline | 40 + 30 + 26 | 4 phases, final phase fell back | 9/0 → 11/0 |
| same | 11:04 | Methane | 13 | delivered, 2 phases | 12/0 |
| Pomodoro timer, `build-interactive-html-widget` | 11:22 | Water | 11 | delivered | 20/0 → 21/0 |
| same | 11:31 | Water | 26 (`validate_html` streaks of 4 and 14) | delivered | 22/0 → 23/0 |

Three readings, none of which trust or skill credit can make today:

1. **Same goal, same recipe, trajectory length varies 1x to 3x.** The 10:47
   run needed 96 L1 tool events and a fallback phase where its two neighbours
   needed 18 and 13 and delivered cleanly. Its skill was credited `success`
   on every phase and Methane's trust rose by two. That is precisely the
   paper's "memorising" regime read through Atoma's counters: the result was
   green and the path was not the recipe.
2. **The repeat is less predictable than the first attempt.** On the pomodoro
   goal, the second run is 2.4x longer than the first, with a fourteen-long
   `validate_html` streak where the first never exceeded two, and it earned
   the same credit. A predictor
   trained on the 11:22 trajectory would have flagged 11:31; nothing did.
3. **The signal is in the ordered tool-name sequence and in its length,
   not in the tool arguments.** The clean trajectories on a shared skill are
   near-identical prefixes (`write_file > start_node_server > fetch_url…`,
   `write_file > start_static_server > validate_html…`). This is what lets
   the predictor stay zero-token and identity-keyed, the same property the
   sentinel's content rules already rely on.

Ten traces is a pilot, not a sample. It establishes that the quantity is
observable and discriminates between runs the current gates treat as equal.
It does not establish a threshold; section 7 refuses to pick one.

## 5. The proposal

### 5.1 One score, one schema

A **trajectory signature** is the ordered list of tool names an L1 actor
emitted for one subtask, plus the executing tier and a cost band. It is
derived from the trace, never declared by a model, so it cannot be spoofed the
way `viaPrefilter` was protected against.

A **trajectory predictor** for a key `(l1AtomId, skillId | capability)` is the
set of signatures observed under that key on the last N credited subtasks. It
is built from the trace store and from nothing else: no verdicts, no expected
outputs, no validator prose. This is the leak-free buffer.

The **predictability score** of a new signature against its predictor is a
bounded edit distance over tool names, normalised by the predictor's median
length, plus a length ratio. Both terms are deterministic and cost nothing.
One schema in `src/contracts/trajectory.ts`; one derivation in one module;
every consumer imports the type.

### 5.2 The three offsets, read for Atoma

The stencil is the part of the paper worth keeping, because it recasts
three questions the repository already asks separately as one quantity:

- **`k=0`, functional coherence:** does this subtask's goal predict this
  subtask's trajectory? The comparison is against the recipe the run was
  given: the compiled manifest for a script skill, the matched skill's
  declared tool set for an LLM skill. A low score means the child did not do
  what it was handed. Today the validator judges this in prose and can only
  withhold credit when it notices; the score makes it mechanical and visible.
- **`k=-1`, backward admissibility:** does this goal predict the trajectory
  the same key took last time? A score that drops from one run to the next
  while results stay green is silent drift. This is the sentinel's measured
  blind spot of 2026-08-23 restated as a number: good result, chaotic path.
- **`k=+1`, forward lookahead:** does the previous goal predict the current
  trajectory? Across runs this measures whether the key's behaviour is
  stable enough to be **compiled**. Promotion today requires earned credit
  and zero failures; it assumes stability it never checks.

The ablation's lesson, that `k=-1` and `k=+1` together beat `k=0` alone, says
where the value is: **index the predictor on the atom and the capability, not
on the run.** A run-local coherence score would reproduce the trust counters'
saturation with more machinery.

### 5.3 Three stages, each one gated by the previous

**Stage A: observe, no power.** A new sentinel rule, `trajectory-drift`,
`kind: 'run.anomaly'`, with the same discipline as `slow-tool-outlier`: it
speaks only once the key has three credited signatures, emits once per
`(runId, l1AtomId, skillId)`, and carries `{score, predictedLen, observedLen,
sampleSize}` in `detail`, never a tool argument. The analyst gains one
question in its review prompt: whether the run's `trajectory-drift` rows are
consistent with its verdict. Nothing else changes. This stage is where a
threshold is **calibrated**, not chosen.

**Stage B: withhold on mismatch.** Once the score separates the 10:47-shaped
runs from their neighbours on a corpus larger than the pilot, a low `k=0`
score becomes a second reason to reach the existing credit gate: the verdict
is still approved, but atom trust, skill credit and promotion are withheld
with a `credit-withheld` skill event whose reasoning names the score. The
fast path is disqualified the same way `proofUncovered` disqualifies it. No
rejection: this obeys "heuristics never reject alone".

**Stage C: predictability as a promotion precondition.** Compiling an LLM
skill to a script additionally requires a stable `k=+1` score over the last
N credited runs of its key. The compiled manifest then becomes the `k=0`
reference for the script's own future runs, closing the loop: a skill is
promoted because its path is predictable, and once promoted its path is what
predictability is measured against.

Stage A can land alone and is worth landing alone. Stages B and C each need
their own measurement on Stage A's journal before they are designed in
detail, and each is a separate COOLING-OFF decision.

## 6. Where it lives

| piece | file | why there |
|---|---|---|
| signature and score schema | `src/contracts/trajectory.ts` | one schema per shape; the sentinel, the credit gate and the analyst all import it |
| signature derivation from a trace window | `src/sentinel/rules.ts` helpers, or a sibling `trajectory.ts` the rules import | it reads `VizEvent[]` and only that; the sentinel already owns "bounded window of events → finding" |
| the predictor store | derived on demand from `runs/*.json` through the existing depth-1 reader, no new product store | `stores.ts` forbids another product store; the predictor is a cache over evidence, not evidence |
| Stage A rule | `src/sentinel/rules.ts`, `id: 'trajectory-drift'` | pure, bounded, journal-only |
| Stage B hook | the credit gate in `src/atoms/L2Atom.ts`, beside `proofUncovered` | one gate, a second reason |
| Stage C precondition | the promotion check in `src/skills/registry.ts` | the one sanctioned path in and out of compilation |
| operator visibility | one `run.anomaly` row per finding; `atoma skills stats` gains a predictability column when Stage C lands | no new surface, no new push kind |

Nothing touches the MCP catalogue, the viz client or the auth surfaces.

## 7. Considered and rejected

- **Embedding similarity on subtask text to build the predictor's key.**
  Rejected: the atoms contract forbids fuzzy matching above the prefilter fast
  path without validation first, and the pilot shows the discriminating
  quantity is the tool sequence, which needs no embedding.
- **A model-scored "did the child follow the plan" call.** Rejected: it exists
  already as the validator's adherence judgment and costs tokens; the point of
  the probe is to be discarded, i.e. free at run time.
- **Scoring on tool arguments or results.** Rejected: model-authored bytes,
  unbounded, and the class of content the sentinel's identity rules deliberately
  stay out of. `argsDigest` may join the key later, never the score.
- **Picking a threshold from the ten pilot traces.** Rejected on purpose. The
  sentinel contract records that its rules are not calibrated and that this is
  the first thing a customer learns; adding an uncalibrated gate with power
  would repeat the 2026-08-14 finding on same-day mechanisms.
- **A run-local `k=0` score as the only signal.** Rejected by the ablation and
  by the saturated trust counters: coherence inside one run is already what the
  validator rewards, and it is exactly what let 10:47 be credited.
- **Storing predictors in `atoma.db`.** Rejected: it would be a second source of
  truth for what the traces already say, and traces are archived and restored
  as evidence while the predictor is disposable.

## 8. Adversarial pass on the proposal itself

Defects found while writing, left visible:

1. **Trajectory length is confounded by goal size.** A longer goal legitimately
   yields a longer path. Mitigation: normalise by the key's median and key on
   `skillId`, whose `when_to_use` already bounds the goal class. Residual risk:
   a skill with a wide `when_to_use` will look noisy; Stage A will show this
   before Stage B can act on it.
2. **Parallel branches interleave.** Fan-out under one L2 mixes several
   children's tool events. Mitigation: signatures are per `(actor, branchId)`;
   the field exists on every event. An event without `actor` is dropped from
   the score, not guessed.
3. **Recovery skills legitimately change the path.** An event-recovery skill
   matched mid-run produces a trajectory the recipe never predicted, and that
   is the correct behaviour. Mitigation: a `skill.match` with a recovery skill
   inside the window suppresses `k=0` for that subtask and is recorded in
   `detail`; `k=-1` and `k=+1` still see the recovery as a legitimate drop.
4. **The predictor can be poisoned by credited-but-wrong runs.** The 10:47 run
   was credited; if it enters the predictor, it widens the tolerance. This is
   the paper's two-phase discipline restated: the predictor must be built from
   runs the analyst graded `sound`, not from every credited run, once Stage A
   gives the analyst the row to grade against. Until then the predictor is
   descriptive only, which is another reason Stage A carries no power.
5. **Goodhart.** Once Stage B lands, a child that learns its path is scored
   could pad its trajectory to match. The score is over tool NAMES emitted by
   the runtime, not over anything the model narrates, and the child never sees
   its score. The residual risk is a supervisor prompt that mentions
   predictability; the proposal says nothing in any prompt.

## 9. Cost

Stage A costs zero tokens and one journal row per finding; the derivation is a
linear pass over a window the sentinel already holds. Stage B costs nothing
extra at run time and may **save** tokens by keeping a chaotic child off the
trust fast path, where its next run would otherwise skip validation. Stage C
removes compile attempts on unstable skills, which are today's most expensive
wasted calls in the skills lifecycle.

## 10. Tests

- Signature derivation: fixtures built from the ten real traces (copied under
  `tests/fixtures/`, since `runs/` is ignored and not an archive), asserting
  the exact sequences printed by section 4's command.
- Score: property tests on the edit distance (identity → 1, disjoint → 0,
  symmetric, length-normalised) and the confounds in section 8 as named cases.
- Stage A rule: the sentinel rule harness, three-sample silence, emit-once
  per key, no argument bytes in `detail`, a throwing derivation is contained.
- Stage B: the existing `credit-withheld` tests gain a second reason and
  prove that the fast path is disqualified while the verdict stays approved.
- Stage C: promotion refused on an unstable key, granted on a stable one, and
  a demotion resets the predictor's window like `resetCounters` resets the
  stamps.

## 11. Open questions for the owner

1. Is `skillId` the right key for the predictor, or should a subtask without
   a matched skill be keyed on the L1 type name alone and accepted as noisier?
2. Stage A as a sentinel rule (live, per run) or as an analyst pass (post
   mortem, across runs)? The sentinel gives the operator the row during the
   run; the analyst is where `k=-1` across runs naturally lives. The proposal
   says both, with the sentinel computing and the analyst reading; is one
   enough to start?
3. Should the predictor be rebuilt from `sound`-graded runs only from day one,
   which makes Stage A depend on analyst coverage, or from every credited run
   with the poisoning risk accepted until Stage B?
4. Is there appetite to run a small armed campaign, the method already used
   for the skills pipeline, to grow the corpus past ten traces before Stage A
   is judged?

## 13. Implementation note, 2026-09-09

Stage A landed the same day, at the owner's explicit request after the
COOLING-OFF concern was raised and reaffirmed. What landed, and where it
departs from the body above:

- The signature, key and score schemas AND the pure derivation live together
  in `src/contracts/trajectory.ts`, not in `src/sentinel`: the analyst's
  digest reads the same quantity and the two subsystems may not import each
  other. `src/sentinel/reference.ts` is the one impure step, reading finished
  traces per corpus, bounded and cached.
- The rule is `trajectory-drift` in `src/sentinel/rules.ts`, journal-only,
  scoring only CLOSED executions (the `llm` event that carries the execution's
  id is the proof), once per execution, element names only.
- The analyst does not read the journal today, so section 5.3's "one question
  about the run's `trajectory-drift` rows" became a mechanical `trajectories`
  block in the digest plus one clause in the `execution` stage of the prompt
  (`ANALYST_PROMPT_VERSION` bumped). Same quantity, read from the trace.
- Open question 1 took the default: keyed on the injected skill, on the
  Molecule alone otherwise, labelled `keyedBy`. Question 2: the sentinel
  computes and journals; the analyst sees the quantity in its digest. Question
  3: every credited run enters the reference, poisoning accepted for a
  descriptive stage. Question 4 was not run; the corpus is still ten traces.
- The floor is armed by default at `TRAJECTORY_DRIFT_DEFAULT_MIN_SCORE` (0.5)
  and is stated everywhere as uncalibrated. On the fixture cut from five real
  traces (`tests/fixtures/sentinel-trajectory-traces.json`) the three readings
  of section 4 order mechanically: a clean repeat scores above 0.8, the 10:47
  first phase between 0.6 and 0.75, the pomodoro streak below 0.5 — and no key
  in those five runs reaches three skill-keyed samples, so the rule would have
  been silent on them. That is the calibration gap Stage A exists to close.
