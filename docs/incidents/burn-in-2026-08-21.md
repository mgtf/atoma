## What was fixed, and what the measurement said afterwards

**1. Two French lines on the runner's stdout** (`9213ced`). That stream is an
API — burn-in parses it — and everything else on it is English.

**2. Skill distillation manufactured SEMANTIC TWINS** (`9213ced`).
`learnSkillFromRun` never showed the model the ids it had to avoid; the only
guard is exact-id equality. Batch 1 learned 11 skills of which **6 were three
twin pairs on the same molecule**. Promotion needs the threshold successes on
ONE id, so two half-credited twins never reach it while both compete for every
match. The distiller now receives the visible namespaces' ids and
`when_to_use` lines and is told to emit the EXISTING id or nothing.

Evidence after: two task-skill distillations have run since, neither a twin
(the whole 12-skill store shows no pair above `--sim 0.35`). That is weak but
consistent. The three RECOVERY skills learned since came through
`learnEventSkillFromRecovery`, a path this fix does not touch.

**3. A synchronous smoke cannot observe what the page updates asynchronously**
(`ab4e9b5`). Batch 1's click-counter spent 19 `validate_html` calls and $0.52
of execute tokens because `#count { transition: all 0.3s ease }` means a
`getComputedStyle` read taken right after the class toggle returns the
PRE-transition value. Trace evidence: `inlineStyle:"red"` beside
`computedColor:"rgb(51, 51, 51)"`. The model "repaired" its already correct
CSS by adding `!important`, which does nothing to an animation. Verified in
Chrome: sync read → `rgb(51, 51, 51)`, async read awaiting 400ms →
`rgb(255, 0, 0)`.

Batch 2 then showed the batch-1 wording ("colour, size or opacity") was too
narrow: `web-stopwatch` regressed and returned
`{ elapsed: 988, running: true, display: "00:00.00" }` — the clock advanced
because `getElapsedMs()` reads `Date.now()`, the display stayed at zero
because the `setInterval` tick could not run. Same mechanism, one level up. So
the guidance now states the LAW and `SMOKE_CANONICAL_STATE_SHAPE` — the
template the model actually copies — is async.

**4. My own regression from that fix** (`7da079e`). The async shape worked (21
of 22 smokes in batch 3's countdown were async) and then the model generalised
"await one repaint" into "await 33 seconds for a countdown". Two smokes were
killed at `CDP_PROTOCOL_TIMEOUT_MS`, each having burned ~45s, and the run
failed on its 900s budget. The await is now BOUNDED, and Puppeteer's
"Increase the 'protocolTimeout' setting" — advice for whoever builds the
harness — is replaced by the remedy the `holdMs` description already gave.

### The Methane routing: hypothesis PROVEN from the trace

The batch-3 prefilter prompt that picked Methane contains, verbatim:
"Already tried and failed THIS task (do NOT pick these): Water" — followed by
a catalog in which NO remaining candidate declares `validate_html`. The
prefilter answered `reuse: Methane` at confidence **high**, which shortcuts
L2 validation by design. So the mechanism is exclusion pressure: the one
capable child was excluded after a legitimate plan rejection, and nothing
checks that a task's capability bucket is satisfiable by any remaining
candidate. The design brief for next session, one reviewed commit:
options are (a) prefilter must `escalate` when no candidate covers the
required bucket (create/branch instead of coach-in-scope), (b) capability-
aware exclusions (an excluded child that is the ONLY bucket holder re-enters
with coaching), (c) enrich the prefilter prompt with per-candidate tool
buckets and an explicit no-candidate rule. Decide against BOTH occurrences'
evidence once a second one exists — or against this one alone if the next
web batch reproduces it.

## The one path six batches never touched: promotion

Promotion is frozen on from-scratch runs by design, so across 28 runs and six
`promotion-eligible` recipes not one was ever compiled. A single SEEDED run
closes that gap — a seeded workspace is the maintenance-mode signal that
enables promotion by default. The seed was batch 6's finished inicheck
workspace (entry, package.json, README, fixtures, a 4-entry manifest) and the
goal was maintenance: add a `--version` flag, document it, then re-verify every
documented invocation.

Delivered at $0.4886 / 17 LLM calls, with `promotions: 2, refusals: 1,
compileErrors: 0, demotions: 0`, and the work is real rather than a banner —
README 64 → 71 lines documenting `node inicheck.js --version`, manifest 4 → 5
entries with that invocation recorded at exit 0.

The three decisions were each correct:

- `build-arg-cli-with-probes` REFUSED, with the reason stated: "the core step
  is designing the CLI's argv-branching logic and exact required output
  strings per invocation from a natural-language spec … the 'design the API
  shape' irreducible LLM step, not a fixed transformation." A design recipe
  must not compile, and the refusal names why.
- `readme-from-probe-evidence` → node script, 5774 chars.
- `recheck-cli-invocations-match-manifest` → node script, 7675 chars.

Every invariant the scripts owe held, checked on disk rather than assumed:
`_fallback.md` present for both (a script without one is undemotable and must
be refused before dispatch), `declaredWrites: ["README.md"]` persisted in
`_meta.json`, `compiledGeneration` stamped, `provenance.mechanism: "compiled"`,
and trust reset to 0✓/0✗ so each new executable earns its own trust before it
can dispatch deterministically. `build-arg-cli-with-probes` carries its
refusal stamp.

No defect found here — which is the result, and it is worth recording as one.
It also confirms the repo's own claim that "compilation's measured value is
maintenance verification, not from-scratch builds": frozen through 28
from-scratch runs, fired on the first maintenance one.

### A second seeded run executed the scripts — one of them

The two compiled scripts sat at 0✓/0✗, so a second seeded maintenance run put
them through the normal L1 tool loop, deliberately on a DIFFERENT artefact
(jsonpick, not the inicheck they were compiled from) to test generalisation
rather than memory. Delivered at $0.2746 / 14 LLM calls, zero fallbacks, zero
demotions, zero compile errors.

`readme-from-probe-evidence` WORKED: written to the sandbox as
`_skill_readme-from-probe-evidence.mjs` at exactly its compiled 5774 bytes,
run via `run_shell`, exit 0, a well-formed single JSON envelope on stdout, and
its first clean success earned — on an artefact it had never seen. That is the
zero-token path doing what it claims.

`recheck-cli-invocations-match-manifest` was matched, injected, and IGNORED.
Its injected block opens "This skill ships an EXECUTABLE script … Your task is
NOT to interpret it", and the child then ran seven `record_probe` calls by hand
instead. The system detected it and withheld credit (`credit-withheld` in the
trace, counter still 0), so the accounting is right — a child that ignored the
recipe proves nothing about it.

Two readings, and only one observation to separate them:

- WORKING AS DESIGNED. AGENTS says plainly that "injection is guidance; it
  never guarantees adherence or credit", and an untrusted script runs through
  the normal tool loop, which is free not to use it.
- A STRUCTURAL TRAP. A compiled script needs three clean successes before it
  may dispatch deterministically. If children keep preferring `record_probe` —
  which both runs AND records, and is the obvious tool for "re-run every
  documented invocation" — this script may never accumulate them, and
  compilation stays unreachable for exactly the recipe class the repo says it
  pays on.

**A third seeded run settled it: variance, not a trap.** Same shape again on a
third artefact (csvhead), and this time the verification script ran —
`write_file _skill_recheck-cli-invocations-match-manifest.mjs`, `run_shell node
_skill_….mjs`, success credited, counter 0 → 1. So the run-2 miss was adherence
variance and the WORKING-AS-DESIGNED reading is the right one: injection is
guidance, and the credit-withholding did its job the one time the child went
its own way. Both compiled scripts now stand at 1✓/0✗, two clean runs short of
deterministic dispatch.

This is the cheapest kind of answer to buy — one extra five-minute run instead
of a paragraph of speculation, and it went against the more interesting of the
two hypotheses.

CONFIRMED MINOR SIGNATURE, two observations: in both runs where a script
executed, the child then deleted it and ran `ls` to confirm the deletion — two
tool calls of cleanup nobody asked for, on every script dispatch. Not worth a
mechanism; worth a sentence in the injected block if it recurs.
